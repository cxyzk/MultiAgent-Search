# 分布式锁实现对比

分布式锁要保证三个特性：**互斥**（同一时刻只有一个持有者）、**不死锁**（持有者崩溃后能释放）、**不误释放**（不会删掉别人的锁）。

## 三种主流实现

| 实现 | 一致性 | 性能 | 复杂度 | 适用 |
|---|---|---|---|---|
| **Redis** | AP（可能丢锁） | 高（万级 QPS） | 低 | 大多数业务场景 |
| **ZooKeeper** | CP（强一致） | 中（千级 QPS） | 中 | 对正确性要求极高 |
| **数据库** | CP | 低 | 低 | 低频、简单场景 |

## Redis 实现（最常用）

### 基础版：SET NX EX

```python
import uuid

def acquire_lock(redis, key: str, ttl: int = 10) -> str | None:
    token = uuid.uuid4().hex
    ok = redis.set(f"lock:{key}", token, nx=True, ex=ttl)
    return token if ok else None

def release_lock(redis, key: str, token: str) -> bool:
    # 必须用 Lua 保证"判断 token + 删除"原子
    script = """
    if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('DEL', KEYS[1])
    end
    return 0
    """
    return redis.eval(script, 1, f"lock:{key}", token) == 1
```

**三个要点**：

1. **`SET NX EX` 一条命令**：不能拆成 `SETNX` + `EXPIRE`（中间崩溃就死锁）
2. **token 校验**：释放时确认是自己的锁，否则会删掉别人的
3. **Lua 原子**：`GET + DEL` 分开执行有竞态

### 进阶：Redisson 的看门狗

TTL 设 10 秒，但业务执行了 30 秒怎么办？Redisson 的**看门狗**（watchdog）每 1/3 TTL 续期一次：

```
t=0    加锁 TTL=30s
t=10   看门狗续期 → TTL=30s
t=20   看门狗续期 → TTL=30s
...
t=35   业务完成，主动释放
```

**注意**：看门狗只在"未指定 leaseTime"时生效。如果显式传了 `leaseTime`，Redisson 不会续期。

## ZooKeeper 实现

利用**临时顺序节点**：

```
/lock
  ├── lock-0000000001  ← 最小序号，持有锁
  ├── lock-0000000002  ← 监听 0001 的删除事件
  └── lock-0000000003  ← 监听 0002
```

- **优点**：会话断开自动删除节点（天然防死锁）；顺序节点保证公平（FIFO）
- **缺点**：每次加锁要创建节点 + 注册监听，性能比 Redis 低一个数量级

## 数据库实现

```sql
-- 唯一索引 + 过期时间
INSERT INTO distributed_lock (lock_key, owner, expire_at)
VALUES ('order:123', 'node-1', NOW() + INTERVAL 10 SECOND)
ON DUPLICATE KEY UPDATE
  owner = IF(expire_at < NOW(), VALUES(owner), owner),
  expire_at = IF(expire_at < NOW(), VALUES(expire_at), expire_at);
```

- **优点**：不用额外组件
- **缺点**：性能差（每次加锁一次 DB 写）；**锁表本身成为瓶颈**

## 一个关键问题：锁丢失

Redis 主从架构下：

```
1. 客户端 A 在 master 加锁成功
2. master 还没同步到 slave 就宕机
3. slave 升为 master，锁丢了
4. 客户端 B 加锁成功 → 两个客户端同时持锁
```

**Redlock**（多 master 投票）试图解决，但**有争议**（Martin Kleppmann 的批评：依赖时钟、无法保证 fencing）。

**工程结论**：

- 锁只用于**性能优化**（避免重复计算），不用于**正确性保证**
- 需要强正确性时，用**数据库唯一约束 / 状态机 / fencing token**

## 选型建议

| 场景 | 推荐 |
|---|---|
| 防止重复提交、缓存重建 | **Redis（SET NX EX）** |
| 定时任务防重复执行 | **Redis + 看门狗** 或 **ZK** |
| 金融级一致性（转账） | **不用分布式锁**，用 DB 事务 + 状态机 |
| 低频场景（每天几次） | **数据库唯一索引** |

## 常见坑

1. **锁的粒度太粗**：`lock:order` 锁住所有订单 → 按 `lock:order:{id}` 分片
2. **TTL 设太短**：业务没执行完锁就过期，两个线程同时进入
3. **释放锁没校验 token**：误删别人的锁
4. **重试风暴**：抢不到锁就立即重试，CPU 打满 → 加随机退避

## FAQ

**Q：Redis 锁能保证绝对互斥吗？**
在主从架构下**不能**（可能丢锁）。单机 Redis 或 Redis Cluster 的单 key 上可以保证。

**Q：看门狗续期会不会一直续下去？**
不会。客户端崩溃后看门狗也停了，TTL 到期自动释放。但**网络分区**时客户端还活着、Redis 连不上，看门狗续期失败，锁会过期——这正是"锁丢失"的场景。
