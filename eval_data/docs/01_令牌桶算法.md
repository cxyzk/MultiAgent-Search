# 令牌桶算法

令牌桶（Token Bucket）是最常用的限流算法之一，核心思想是"以恒定速率往桶里放令牌，请求取走令牌才能通过"。

## 基本原理

桶有两个关键参数：

- **容量（capacity）**：桶里最多能存多少个令牌，决定了**允许的最大突发量**
- **填充速率（rate）**：每秒往桶里放多少个令牌，决定了**长期平均速率**

请求到来时：

1. 先按 `(now - last_refill) * rate` 补充令牌，但不超过容量
2. 桶里有令牌 → 取走一个，放行
3. 桶里没有令牌 → 拒绝（或排队等待）

因为是"先攒后取"，令牌桶**允许一定程度的突发流量**：桶满时可以瞬间放行 capacity 个请求。

## 参数怎么定

| 场景 | capacity | rate | 说明 |
|---|---|---|---|
| 普通 API | 100 | 50 QPS | 允许 2 秒的突发 |
| 支付接口 | 20 | 10 QPS | 突发窗口要小 |
| 批量导入 | 1000 | 100 QPS | 允许一次性大批量 |
| 短信发送 | 10 | 5 QPS | 成本敏感，保守 |

经验公式：**capacity ≈ rate × 可接受突发秒数**。比如 rate=50、允许 2 秒突发，capacity 就设 100。

## 实现示例（Python）

```python
import time

class TokenBucket:
    def __init__(self, rate: float, capacity: int):
        self.rate = rate            # 每秒补充的令牌数
        self.capacity = capacity    # 桶容量
        self.tokens = capacity      # 初始满桶
        self.last = time.monotonic()

    def allow(self, n: int = 1) -> bool:
        now = time.monotonic()
        # 按时间差补令牌（惰性计算，不需要定时任务）
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= n:
            self.tokens -= n
            return True
        return False
```

**关键点**：用"惰性补令牌"（按时间差计算）而不是起一个定时器，避免线程开销和精度问题。

## 与漏桶的区别

| 维度 | 令牌桶 | 漏桶 |
|---|---|---|
| 突发流量 | **允许**（桶里攒的令牌可一次性消耗） | **不允许**（恒定速率流出） |
| 参数 | rate + capacity | rate + 队列容量 |
| 典型用途 | API 网关、对外接口 | 消息消费、下游保护 |
| 超限行为 | 立即拒绝 | 排队等待（队列满才丢） |

一句话：**令牌桶管"平均速率 + 允许突发"，漏桶管"绝对平滑"**。

## 常见坑

1. **capacity 设成 1**：等于退化成固定速率，失去突发能力
2. **rate 用整数除法**：`tokens += (now-last) * rate` 里如果 tokens 是 int，会丢掉小数，长期偏差明显
3. **多线程不加锁**：`tokens` 的读改写不是原子的，高并发下会多放行

## FAQ

**Q：令牌桶能保证绝对不超过 QPS 吗？**
不能。它保证的是**长期平均速率 ≤ rate**，但允许瞬时突发（最多 capacity 个）。要绝对不超，得用漏桶。

**Q：Redis 里怎么实现分布式令牌桶？**
用 Lua 脚本把"取令牌"做成原子操作，key 存 `tokens` 和 `last_refill_ts` 两个字段，每次调用时在脚本里补令牌、判断、扣减。
