# 限流与熔断降级的区别

限流、熔断、降级经常被混为一谈，但它们解决的问题完全不同，触发条件和效果也不一样。

## 一句话区分

- **限流**：主动控制**进入**的流量，超了就拒
- **熔断**：被动检测**下游**的失败率，失败多了就暂时不调用
- **降级**：返回**兜底内容**，保证核心链路可用

## 对比表

| 维度 | 限流 | 熔断 | 降级 |
|---|---|---|---|
| 触发条件 | 流量超过阈值 | 下游失败率/慢调用比例超阈值 | 主动开关 / 熔断触发 |
| 作用对象 | 入口流量 | 下游依赖 | 功能或数据的完整性 |
| 状态 | 无状态（每次判断） | **三态**：关闭 / 打开 / 半开 | 无状态 |
| 恢复方式 | 自动（令牌补充） | 半开探测成功后关闭 | 手动或自动恢复 |
| 用户感知 | 429 限流 | 快速失败（可能报错） | 返回缓存/默认值，**体验更好** |

## 熔断器的三个状态

```
    失败率超阈值
CLOSED ──────────────→ OPEN
  ↑                      │
  │   探测成功            │ 等待窗口结束
  └──── HALF_OPEN ←──────┘
          │
          └─ 探测失败 → 回到 OPEN
```

- **CLOSED**：正常调用下游
- **OPEN**：直接返回失败，不再调用（保护下游 + 快速失败）
- **HALF_OPEN**：放少量请求试探，成功则关闭，失败则继续打开

**关键参数**：

| 参数 | 典型值 | 说明 |
|---|---|---|
| 失败率阈值 | 50% | 10 次调用中 5 次失败就打开 |
| 最小请求数 | 10 | 样本太少不触发（避免 1/1 就熔断） |
| 打开时长 | 30s | 30 秒后进入半开 |
| 半开放行数 | 3-5 | 试探请求数 |

## 降级的四种手段

1. **返回缓存**：商品详情挂了，返回 5 分钟前的快照
2. **返回默认值**：推荐服务挂了，返回热门榜兜底
3. **功能裁剪**：评论服务挂了，页面隐藏评论区，主体照常
4. **异步补偿**：下单积分服务挂了，先记消息队列，稍后补

## 三者怎么配合

一个典型的电商下单链路：

```
用户请求
  → [网关限流] 挡住洪水（如 5000 QPS）
  → [订单服务] 调用 [库存服务]
       ├─ 库存服务失败率 > 50% → [熔断] 打开
       └─ 熔断打开期间 → [降级] 返回"库存查询中，稍后确认"
```

**限流是第一道闸，熔断是第二道保险，降级是最后的安全网。**

## 常见坑

1. **只限流不熔断**：限流按"请求数"算，但如果下游变慢，限流放行的请求仍会拖垮连接池
2. **熔断阈值设太低**：`失败率 10%` 在正常抖动时频繁误熔断
3. **降级返回脏数据**：缓存快照没有版本号，降级后用户看到过期价格引发客诉
4. **降级没有监控**：降级悄悄生效，团队不知道核心功能已经不可用

## FAQ

**Q：限流能代替熔断吗？**
不能。限流假设"下游能处理我放行的量"，但下游可能因为自身 bug 变慢/报错，这时限流毫无作用。熔断检测的是**结果质量**。

**Q：熔断打开后，用户看到什么？**
取决于降级策略。最差是 503，最好是返回缓存/默认值。**熔断只是"不再调用下游"，展示什么由降级决定**。

**Q：Sentinel 和 Hystrix 的区别？**
Hystrix（已停止维护）以线程池隔离为主，Sentinel 以信号量 + 滑动窗口统计为主，支持更细的流控规则（QPS/并发/热点参数）。
