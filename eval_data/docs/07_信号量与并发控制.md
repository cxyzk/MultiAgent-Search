# 信号量与并发控制

信号量（Semaphore）控制的是"同时进行的数量"，而不是"单位时间的速率"。这是它和限流器最本质的区别。

## 限流 vs 并发控制

| | 限流器（令牌桶） | 信号量 |
|---|---|---|
| 控制对象 | **每秒请求数**（QPS） | **同时执行数**（并发度） |
| 维度 | 时间窗口 | 瞬时状态 |
| 超限行为 | 拒绝 / 排队 | 阻塞等待 / 立即失败 |
| 典型用途 | 保护入口 | **保护资源**（连接池、下游并发） |

**关键区别**：限流器假设"每个请求很快完成"，信号量不关心耗时——一个请求处理 10 秒，它就占用一个许可 10 秒。

## 典型场景

### 1. 限制下游并发

下游服务只能承受 20 个并发连接，但上游 QPS 很高：

```python
import asyncio

sem = asyncio.Semaphore(20)

async def call_downstream(payload):
    async with sem:                    # 超过 20 个请求在这里排队
        return await http_client.post("/api", json=payload)
```

### 2. 数据库连接池

连接池本质就是信号量：`max_connections=50` 意味着最多 50 个并发使用连接，第 51 个请求等待或失败。

### 3. 限制文件句柄 / 内存占用

批量导出任务同时跑 5 个（每个占 500MB 内存），用信号量 5 控制。

## 公平性问题

大多数信号量实现**不保证 FIFO**：释放许可时，可能被后到的请求抢到，导致先到的请求饿死。

- **Java**：`new Semaphore(n, true)` 开启公平模式（代价是性能下降约 10-20%）
- **Python asyncio**：`asyncio.Semaphore` 的等待队列是 FIFO 的
- **Go**：`golang.org/x/sync/semaphore` 提供加权信号量，也是 FIFO

## 超时控制（必备）

```python
try:
    await asyncio.wait_for(sem.acquire(), timeout=0.5)
except asyncio.TimeoutError:
    raise TooManyRequests("并发已满，请稍后重试")
```

**不设超时会出大问题**：下游变慢 → 请求在信号量上堆积 → 连接/内存被占满 → 整个服务雪崩。

## 加权信号量

不同请求消耗不同许可（如大查询消耗 5 个、小查询消耗 1 个）：

```go
sem := semaphore.NewWeighted(100)
if err := sem.Acquire(ctx, 20); err != nil {  // 大查询要 20 个
    return err
}
defer sem.Release(20)
```

适合"资源消耗差异大"的场景（如按返回行数、按文件大小限制）。

## 常见坑

1. **acquire 后异常路径没 release**：许可泄漏，最终信号量耗尽 → 必须用 `try/finally` 或 `with`
2. **信号量数量按"实例数"算错**：4 个实例各 20 个许可，对下游就是 80 并发
3. **和线程池混用**：线程池的队列 + 信号量双重排队，延迟叠加，容易超时

## FAQ

**Q：信号量和熔断器什么关系？**
熔断器是"检测到下游持续失败就快速失败"，信号量是"限制并发数"。两者常组合：信号量控并发，熔断器控失败率。

**Q：信号量能代替限流吗？**
不能完全代替。信号量不限 QPS，如果每个请求都很快（1ms），20 个许可能撑 2 万 QPS；但如果请求变慢到 1 秒，同样 20 个许可只能撑 20 QPS。**信号量保护资源，限流器保护入口**。

**Q：Python 的 asyncio.Semaphore 有公平性保证吗？**
有，等待中的协程按 FIFO 顺序唤醒（CPython 3.8+ 实现）。
