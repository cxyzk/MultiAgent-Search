# 接口超时与重试

超时和重试是一对孪生问题：**超时设置不对会拖垮自己，重试策略不对会打垮下游**。

## 超时怎么设

### 原则：逐层递减

```
客户端超时（5s） > 网关超时（4s） > 服务A超时（3s） > 服务B超时（2s） > DB超时（1s）
```

每一层都要比下游**略大**，否则下游还在处理、上游已经超时重试，导致重复执行。

### 参考值

| 类型 | 超时 | 说明 |
|---|---|---|
| 缓存（Redis） | 50-100ms | 超过就说明网络有问题，走降级 |
| 数据库查询 | 1-3s | 慢查询要单独治理，不能靠调大超时 |
| 内部 RPC | 500ms-2s | 按 P99 延迟 × 3 |
| 第三方 API | 3-5s | 不可控，必须设 |
| 前端请求 | 10s | 超过用户就认为卡死 |

## 重试的三个前提

1. **操作可重入**（幂等）——否则重试会造成重复扣款/重复下单
2. **失败可恢复**——网络抖动可以重试，参数错误重试多少次都没用
3. **有上限**——无限重试会把下游打死

## 重试策略

### 指数退避 + 抖动

```python
import random
import time

def retry_with_backoff(fn, max_attempts=3, base=0.2):
    for attempt in range(max_attempts):
        try:
            return fn()
        except RetryableError:
            if attempt == max_attempts - 1:
                raise
            # 0.2s, 0.4s, 0.8s + 随机抖动
            delay = base * (2 ** attempt) + random.uniform(0, 0.1)
            time.sleep(delay)
```

**为什么要加抖动（jitter）**：如果 1000 个客户端同时失败、同时按固定间隔重试，会形成"重试风暴"，一波一波打向下游。

### 哪些错误值得重试

| 错误类型 | 重试 | 说明 |
|---|---|---|
| 网络超时 / 连接重置 | ✅ | 典型可恢复 |
| 503 / 502 / 504 | ✅ | 服务暂时不可用 |
| 429 Too Many Requests | ✅（带 Retry-After） | 按服务端指示等待 |
| 400 参数错误 | ❌ | 重试也不会变对 |
| 401 / 403 | ❌ | 权限问题 |
| 500 内部错误 | ⚠️ 谨慎 | 可能是 bug，重试会放大问题 |

## 重试的三种实现层次

```
① SDK 层重试（如 HTTP 客户端）    —— 无感知，但容易重试不该重试的
② 业务层重试（显式 try-catch）    —— 可控，能区分错误类型
③ 网关/代理层重试（Nginx/Envoy）  —— 统一，但对业务无感知
```

**推荐**：**业务层重试为主**（能判断幂等性和错误类型），SDK 层重试关掉或设很小。

## 超时 + 重试的组合陷阱

### 陷阱 1：超时时间 × 重试次数 > 上游超时

```
下游超时 3s，重试 3 次 → 最坏 9s
但上游（网关）超时只有 5s
→ 第 3 次重试还没开始，上游已经断开
```

**修法**：重试总时长（含退避）必须小于上游超时。

### 陷阱 2：重试放大了雪崩

下游已经过载（响应变慢），重试让请求量翻 3 倍 → 彻底打挂。

**修法**：

- 重试前先检查**熔断器状态**（打开状态直接失败，不重试）
- 用**重试预算**（如整个服务重试率不超过 10%）

### 陷阱 3：读请求重试没问题，写请求重试出事

```python
# 危险：支付请求超时后重试，可能扣两次款
pay(order_id, amount)   # 超时了，但钱已经扣了
```

**修法**：写操作必须带**幂等 key**，重试时用同一个 key。

## 一个生产配置示例

```python
import httpx

client = httpx.Client(
    timeout=httpx.Timeout(
        connect=0.5,      # 建连超时
        read=2.0,         # 读超时
        write=1.0,        # 写超时
        pool=0.5,         # 从连接池取连接的超时
    ),
    limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
)
```

**注意 `pool` 超时**：连接池耗尽时，请求会在"等连接"上无限阻塞——很多线上事故是这里没设超时。

## 常见坑

1. **只设了总超时，没设连接超时**：DNS 解析卡住 30 秒
2. **重试没有退避**：立即重试，下游还没恢复
3. **重试不区分错误**：400 错误也重试，浪费 3 倍资源
4. **超时时间拍脑袋**：没看 P99 延迟，设成 100ms 导致大量误超时

## FAQ

**Q：超时了到底该不该重试？**
看操作是否幂等。**查询类默认重试**（1-2 次），**写入类只在有幂等 key 时重试**。

**Q：gRPC 的重试和 HTTP 有什么不同？**
gRPC 支持"透明重试"（服务端配置 retry policy，客户端自动执行），但要配合 `grpc-retry-pushback-ms` 做服务端背压。

**Q：重试次数设 3 次合理吗？**
大多数场景 2-3 次足够。超过 3 次说明下游有持续性问题，应该熔断而不是重试。
