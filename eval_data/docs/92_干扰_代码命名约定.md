# 代码命名约定

本文规定团队的命名规范，覆盖变量、函数、类、常量、文件和数据库字段。

## 通用原则

1. **见名知意**：`user_count` 而不是 `uc`
2. **避免缩写**：`message` 而不是 `msg`（除非是行业通用缩写）
3. **不用拼音**：`订单` 用 `order`，不用 `dingdan`
4. **长度适中**：3-30 字符，太短没信息量，太长难读

## Python

| 类型 | 规范 | 示例 |
|---|---|---|
| 变量/函数 | snake_case | `user_count` `get_order_by_id` |
| 类 | PascalCase | `OrderService` `PaymentResult` |
| 常量 | UPPER_SNAKE | `MAX_RETRY_COUNT` |
| 私有成员 | 前缀下划线 | `_cache` `_internal_method` |
| 模块 | 短小写 | `order_service.py` |

**函数命名用动词开头**：

```python
# 好
def calculate_total_price(items): ...
def is_valid_order(order): ...

# 不好
def total(items): ...          # 名词，看不出做什么
def order_check(order): ...    # 动词在后
```

**布尔值用 is/has/can 前缀**：

```python
is_active = True
has_permission = False
can_retry = True
```

## JavaScript/TypeScript

| 类型 | 规范 | 示例 |
|---|---|---|
| 变量/函数 | camelCase | `userCount` `getOrderById` |
| 类/组件 | PascalCase | `OrderService` `ChatBubble` |
| 常量 | UPPER_SNAKE | `API_BASE_URL` |
| 类型/接口 | PascalCase | `OrderDetail` `ChatMessage` |
| 文件（组件） | PascalCase | `ChatBubble.vue` |
| 文件（工具） | camelCase | `formatDate.ts` |

**Vue 组件命名**：多个单词（`ChatBubble` 而不是 `Chat`），避免和 HTML 标签冲突。

## 数据库

| 对象 | 规范 | 示例 |
|---|---|---|
| 表名 | 复数 snake_case | `orders` `user_profiles` |
| 字段 | snake_case | `created_at` `user_id` |
| 主键 | `id` | `id BIGINT PRIMARY KEY` |
| 外键 | `{表名单数}_id` | `user_id` `order_id` |
| 索引 | `idx_{表}_{字段}` | `idx_orders_user_id` |
| 唯一索引 | `uk_{表}_{字段}` | `uk_users_email` |

**时间字段统一**：`created_at` `updated_at` `deleted_at`（软删除），不要用 `create_time`/`ctime` 混着来。

## API 路径

```
GET    /api/v1/orders            # 列表
GET    /api/v1/orders/{id}       # 详情
POST   /api/v1/orders            # 创建
PUT    /api/v1/orders/{id}       # 全量更新
PATCH  /api/v1/orders/{id}       # 部分更新
DELETE /api/v1/orders/{id}       # 删除
```

**规范**：

- 资源用**复数名词**（`orders` 不是 `order`）
- **动作用 HTTP 方法**，不要出现在路径里（`/getOrder` ✗）
- 版本号放路径（`/v1/`），不要放 header
- 多单词用 **kebab-case**（`/order-items`）

## 常见错误

| 错误 | 正确 | 原因 |
|---|---|---|
| `data` `info` `temp` | `order_detail` `payment_result` | 无信息量 |
| `list1` `list2` | `pending_orders` `completed_orders` | 编号无意义 |
| `getUserInfo()` | `get_user(id)` | 冗余 |
| `flag` | `is_deleted` | 不知道 flag 什么意思 |
| `OrderServiceManagerImpl` | `OrderService` | 过度包装 |

## 命名评审

Code Review 时，命名问题**必须提**——因为改名成本随时间指数增长：

- 开发阶段改名：5 分钟
- 上线后改名：改代码 + 改测试 + 改文档 + 数据迁移，可能几天

## FAQ

**Q：缩写到底能不能用？**
行业通用的可以（`id` `url` `http` `api`），自创的不要。判断标准：新人看到能不能立刻理解。

**Q：函数名多长算合适？**
`get_user_orders_by_status_and_date_range` 虽然长，但比 `get_orders` 清晰。**宁可长一点，不要有歧义**。

**Q：历史代码命名不规范怎么办？**
不要一次性全改（风险大）。新代码遵守规范，改到相关文件时顺手改，逐步收敛。
