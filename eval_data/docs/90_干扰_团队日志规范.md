# 团队日志规范

本文规定团队日志的格式、级别和内容要求，所有服务必须遵守。

## 日志级别

| 级别 | 使用场景 | 示例 |
|---|---|---|
| ERROR | 需要人工介入的失败 | 支付回调处理失败、DB 连接池耗尽 |
| WARN | 可自愈但需要关注 | 重试成功、降级触发、慢查询 |
| INFO | 关键业务节点 | 订单创建、状态变更、定时任务开始/结束 |
| DEBUG | 排查用的细节 | 请求参数、SQL、缓存命中情况 |

**原则**：

- **ERROR 必须告警**，不告警的 ERROR 说明级别用错了
- **INFO 不要刷屏**，高频循环里不打 INFO
- **DEBUG 生产默认关闭**，需要时动态开启

## 格式规范

### 统一 JSON 格式

```json
{
  "ts": "2026-10-30T10:23:45.123+08:00",
  "level": "INFO",
  "service": "order-service",
  "trace_id": "a1b2c3d4e5f6",
  "span_id": "001",
  "msg": "order created",
  "order_id": "ORD20261030001",
  "user_id": 12345,
  "amount": 199.00,
  "duration_ms": 45
}
```

**必填字段**：`ts` `level` `service` `trace_id` `msg`

**为什么用 JSON**：便于 ELK/Loki 结构化查询，不用写正则解析。

### 日志内容要求

1. **msg 用英文短句**（便于统一检索），关键信息放结构化字段
2. **必须带 trace_id**：跨服务串联的基础
3. **金额/数量用数值类型**，不要拼进 msg 字符串
4. **异常必须带堆栈**：`logger.error("failed", exc_info=True)`

## 禁止事项

| 禁止 | 原因 |
|---|---|
| 打印密码、token、身份证、银行卡 | 安全合规 |
| 打印完整请求体（可能含敏感信息） | 用字段白名单 |
| 在循环里打 INFO | 日志量爆炸 |
| `print` / `console.log` | 无法统一收集 |
| 用字符串拼接 JSON | 转义错误导致解析失败 |

## 日志量与成本

按 1000 QPS、每请求 2 条日志、每条 500 字节算：

```
1000 × 2 × 500 × 86400 ≈ 86GB/天
```

**控制手段**：

1. **采样**：DEBUG 日志按 1% 采样
2. **分级存储**：ERROR 存 90 天，INFO 存 7 天，DEBUG 存 1 天
3. **压缩**：日志压缩后体积约为原始的 1/10

## 排查流程

1. 从告警或用户反馈拿到 **trace_id**
2. 在 Kibana/Loki 里按 trace_id 查全链路日志
3. 按时间排序，找第一个 ERROR 或耗时突增的 span
4. 结合 metric（CPU/连接数/QPS）确认是代码问题还是资源问题

## FAQ

**Q：日志和链路追踪（Tracing）什么关系？**
日志记录"发生了什么"，Tracing 记录"调用了谁、花了多久"。两者通过 trace_id 关联，缺一不可。

**Q：日志要不要脱敏？**
必须。手机号中间 4 位、身份证后 8 位、银行卡全部要脱敏，且脱敏要在**写入日志前**完成。

**Q：多语言服务怎么统一格式？**
用统一的日志规范文档 + 各语言的封装库（Java 用 logback-json，Python 用 structlog，Go 用 zap），保证字段名一致。
