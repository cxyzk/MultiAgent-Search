# 限流系统设计复盘（长文）

本文复盘一次从零搭建分布式限流系统的完整过程，包括需求分析、方案选型、踩坑记录和最终架构。适合需要理解"限流系统如何落地"的读者。

## 一、背景

公司业务快速增长，核心 API 的 QPS 从 500 涨到 8000，期间发生过三次因流量突增导致的雪崩：

- **第一次**：营销活动推送，10 分钟内 QPS 从 800 飙到 5000，DB 连接池打满，全站 500
- **第二次**：爬虫扫接口，单 IP 每秒 300 请求，拖垮了商品详情服务
- **第三次**：上游服务重试风暴，一次网络抖动触发了 3 倍流量

三次事故的共性是：**没有任何限流措施**，流量直接打到最脆弱的 DB 层。

## 二、需求梳理

### 功能需求

1. **多维度限流**：全局、接口、用户、IP
2. **动态调整**：不改代码、不重启，5 分钟内生效
3. **精细化**：不同接口不同阈值（下单 100 QPS，查询 2000 QPS）
4. **可观测**：实时看到各维度限流触发次数

### 非功能需求

| 指标 | 要求 |
|---|---|
| 限流判断延迟 | < 2ms（P99） |
| 可用性 | 99.99%（限流组件不能成为故障源） |
| 性能损耗 | < 5% |
| 故障降级 | Redis 不可用时自动切本地限流 |

## 三、方案选型

### 候选方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Nginx limit_req | 性能最好、零开发 | 只能按 IP/路径，拿不到用户身份 | 作为最外层兜底 |
| Spring Cloud Gateway | 集成方便 | 只适用 Java 技术栈 | 部分服务用 |
| Sentinel | 功能全、控制台好用 | 侵入性强、规则分散 | **未采用** |
| 自研 Redis 限流 | 完全可控、多语言通用 | 要自己实现和运维 | **最终选择** |

### 为什么自研

团队技术栈混杂（Java/Go/Python），需要一个**语言无关**的限流方案。自研的核心只有两部分：

1. **Redis + Lua 的令牌桶**（约 200 行）
2. **配置中心推送规则**（复用现有 Nacos）

## 四、核心设计

### 4.1 数据结构

```
rate:{维度}:{值}:{接口}  →  Hash { tokens, ts }
```

例子：

```
rate:user:12345:/api/order     → {tokens: 87.3, ts: 1730000000000}
rate:ip:10.0.0.1:/api/search   → {tokens: 1950, ts: 1730000000000}
rate:global:*                   → {tokens: 7900, ts: 1730000000000}
```

**为什么用 Hash 而不是 String**：需要同时存 tokens 和 ts，两个字段必须原子读写。

### 4.2 Lua 脚本

```lua
-- KEYS[1]: rate key
-- ARGV[1]: now_ms, ARGV[2]: rate(每秒), ARGV[3]: capacity, ARGV[4]: cost
local now = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local capacity = tonumber(ARGV[3])
local cost = tonumber(ARGV[4])

local data = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1])
local last = tonumber(data[2])

if tokens == nil then
    tokens = capacity
    last = now
end

-- 惰性补充令牌
tokens = math.min(capacity, tokens + (now - last) / 1000 * rate)

local allowed = 0
if tokens >= cost then
    tokens = tokens - cost
    allowed = 1
end

redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- TTL 按"桶从空到满需要的时间"设置，避免 key 堆积
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) + 60000)

return {allowed, math.floor(tokens)}
```

**几个设计细节**：

- **TTL 动态计算**：`capacity/rate` 秒后才能重新满桶，超过这个时间 key 可以安全删除
- **返回剩余令牌**：客户端可以据此做自适应（剩余少时降级）
- **cost 参数**：支持加权（大查询消耗 5 个令牌）

### 4.3 多维度叠加

一个请求要过三道关：

```python
def check(request) -> bool:
    checks = [
        ("global", "*", 10000, 20000),          # 全局限流
        ("ip", request.ip, 100, 200),           # 单 IP
        ("user", request.user_id, 50, 100),     # 单用户
    ]
    for dim, value, rate, capacity in checks:
        allowed, left = redis_token_bucket(f"rate:{dim}:{value}:{request.path}", rate, capacity)
        if not allowed:
            return False
    return True
```

**顺序很重要**：从粗到细，先挡全局（成本最低），再挡用户。

**性能优化**：三道 Redis 调用可以 Pipeline 合并成一次往返（约 0.3ms）。

## 五、踩过的坑

### 坑 1：Lua 脚本里用了应用时间

最初脚本用客户端传入的 `now`，多实例时钟不同步时（NTP 偏差 2 秒），令牌计算错乱，出现"明明没超限却被拒"。

**修法**：脚本里用 `redis.call('TIME')` 取 Redis 时间，所有实例以 Redis 为准。

### 坑 2：Key 数量爆炸

按 `用户ID + 接口` 维度限流后，Redis 里出现了 **800 万个 key**，内存从 2GB 涨到 12GB。

**原因**：短 TTL 的 key 太多，Redis 的过期删除跟不上。

**修法**：

- 降低维度：只对核心接口做用户级限流（从 100 个接口降到 8 个）
- 缩短 key：`u:123:o` 代替 `rate:user:12345:/api/order`
- 用 Redis Cluster 分片

### 坑 3：Redis 抖动导致限流全拒

一次 Redis 主从切换（约 8 秒），所有限流请求超时，客户端按"失败即拒绝"处理，**全站 503 持续 8 秒**。

**修法**：改为 **fail-open + 本地兜底**：

```python
try:
    allowed = redis_check(...)
except RedisTimeout:
    allowed = local_bucket.check(...)   # 本地令牌桶，限额 = 全局限额 / 实例数
```

### 坑 4：限流阈值拍脑袋

最初"下单接口 100 QPS"是拍脑袋定的，结果大促时正常流量就被限了。

**修法**：压测 + 埋点。用历史 P99 流量 × 2 作为初始阈值，再按实际拒绝率调整。

## 六、最终架构

```
客户端
  ↓
Nginx（IP 级，10r/s）
  ↓
网关（全局 + 接口级，Redis 令牌桶）
  ↓
业务服务（用户级，本地令牌桶 + Redis 同步）
  ↓
DB / 缓存
```

**三层限流的分工**：

| 层 | 维度 | 阈值 | 作用 |
|---|---|---|---|
| Nginx | IP | 10 r/s | 挡爬虫、刷接口 |
| 网关 | 全局/接口 | 10000/2000 | 挡流量洪峰 |
| 业务 | 用户 | 50 | 防单用户滥用 |

## 七、效果

| 指标 | 上线前 | 上线后 |
|---|---|---|
| 因流量导致的 5xx | 每月 2-3 次 | 0 次（3 个月） |
| DB 最大连接数 | 打满（500） | 峰值 320 |
| 限流误杀率 | — | 0.03% |
| 限流判断延迟 P99 | — | 1.2ms |

## 八、经验总结

1. **限流不是"加个组件"**，是"梳理流量模型"——先搞清楚哪些接口重要、能承受多少
2. **阈值必须压测得出**，拍脑袋的阈值上线必出事
3. **降级策略比限流本身更重要**——Redis 挂了怎么办，要在设计阶段想清楚
4. **可观测性是刚需**——没有监控的限流等于没有限流，你不知道它在不在工作
5. **从简到繁**：先 Nginx 粗限，再上分布式限流，不要一开始就搞复杂架构
