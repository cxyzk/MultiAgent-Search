# 漏桶算法

漏桶（Leaky Bucket）把请求看作"往桶里倒水"，桶底有一个固定速率的孔，水以恒定速度漏出。超出桶容量的水直接溢出（丢弃）。

## 核心特征：绝对平滑

漏桶的输出速率**恒定**，与输入速率无关：

```
输入（可能突发）→ [ 队列容量 N ] → 恒定速率流出
                     ↑ 满了就丢
```

这带来两个结论：

- **优点**：下游永远只承受固定速率，保护效果最强
- **缺点**：突发请求会被排队或丢弃，**响应延迟不确定**

## 参数

| 参数 | 含义 | 典型值 |
|---|---|---|
| rate | 每秒处理请求数 | 100 QPS |
| capacity | 队列最大长度 | 200（约 2 秒缓冲） |
| 等待超时 | 排队超过多久就放弃 | 500ms |

**capacity 的取舍**：

- 太小 → 突发时大量丢弃
- 太大 → 队列积压，用户等很久才拿到 429/超时

经验值：`capacity ≈ rate × 可接受等待秒数`。rate=100、能忍 2 秒，capacity 就设 200。

## 实现示例（Go）

```go
type LeakyBucket struct {
    rate     time.Duration // 每个请求的处理间隔，如 10ms
    capacity int
    queue    chan struct{}
}

func NewLeakyBucket(rate time.Duration, capacity int) *LeakyBucket {
    b := &LeakyBucket{rate: rate, capacity: capacity, queue: make(chan struct{}, capacity)}
    go func() {
        ticker := time.NewTicker(rate)
        for range ticker.C {
            select {
            case <-b.queue: // 每 tick 放行一个
            default:
            }
        }
    }()
    return b
}

func (b *LeakyBucket) Allow() bool {
    select {
    case b.queue <- struct{}{}:
        return true
    default:
        return false // 队列满，直接拒绝
    }
}
```

## 与令牌桶的选择

| 你的诉求 | 选哪个 |
|---|---|
| 对外 API，允许用户偶尔突发 | **令牌桶** |
| 保护脆弱的下游（老系统、第三方接口） | **漏桶** |
| 消息消费限速，要求平稳 | **漏桶** |
| 需要"排队等待"而不是"立即拒绝" | **漏桶** |

**实际工程里令牌桶更常见**——因为用户体验上"突发被允许"比"绝对平滑"更重要，而下游保护通常用"熔断 + 队列"组合解决。

## 常见坑

1. **用 sleep 实现漏桶**：每个请求 sleep 一段时间会让处理线程被占满，应该用队列 + 定时器
2. **队列无界**：OOM 风险，必须设 capacity
3. **只限入口不限出口**：入口漏桶 + 无限并发调用下游，下游照样被打挂

## FAQ

**Q：漏桶和"固定窗口限流"什么关系？**
固定窗口是"统计窗口内请求数"，超了拒绝；漏桶是"控制流出速度"。前者有窗口边界突刺问题，后者没有，但后者延迟更高。

**Q：Nginx 的 limit_req 是哪种？**
`limit_req` 用的是**漏桶**（burst 参数就是队列容量），`limit_req_status` 是溢出时的状态码。
