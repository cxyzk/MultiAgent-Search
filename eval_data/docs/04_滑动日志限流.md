# 滑动日志限流

滑动日志（Sliding Log）是精度最高的限流方案：**记录每个请求的时间戳**，判断"最近 N 秒内的请求数是否超限"。

## 与滑动窗口的区别

| | 滑动窗口（格子） | 滑动日志 |
|---|---|---|
| 存储 | N 个计数器（按时间格子聚合） | 每个请求一条时间戳 |
| 精度 | 格子粒度（如 100ms） | **精确到毫秒** |
| 内存 | O(格子数) | **O(请求数)** |
| 典型实现 | Redis Hash 计数器 | Redis ZSET |

滑动日志本质是"滑动窗口的格子数 = 请求数"的极限情况——每个请求占一个格子。

## 实现（Redis ZSET，带 Lua 原子化）

```lua
-- KEYS[1] = rate:key
-- ARGV[1] = now_ms, ARGV[2] = window_ms, ARGV[3] = limit
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
local count = redis.call('ZCARD', KEYS[1])
if count < limit then
    redis.call('ZADD', KEYS[1], now, now .. '-' .. math.random(1000000))
    redis.call('PEXPIRE', KEYS[1], window)
    return 1
end
return 0
```

**必须用 Lua**：`ZREMRANGEBYSCORE + ZCARD + ZADD` 三步如果分开执行，高并发下会超发。

## 内存估算

假设限制 **1000 请求/分钟**：

- 每个成员：约 50 字节（时间戳字符串 + ZSET 开销）
- 1000 个成员 ≈ **50KB / key**
- 10 万个 key（按用户维度）≈ **5GB**

**这就是滑动日志不能用于高 QPS 的原因**。同样的限制用令牌桶只需要 2 个字段（约 100 字节）。

## 什么场景适合

| 场景 | 限流值 | 为什么合适 |
|---|---|---|
| 登录失败次数 | 5 次/分钟 | QPS 极低，精度要求高 |
| 短信验证码 | 1 条/分钟 | 必须精确，不能多给 |
| 支付密码错误 | 3 次/小时 | 安全敏感 |
| 单用户导出 | 5 次/天 | 低频、成本高 |

共同点：**限制值小（个位数到几十）、时间窗长（分钟/小时/天）、安全或成本敏感**。

## 常见坑

1. **成员用纯时间戳**：同一毫秒的多个请求会互相覆盖（ZSET 成员唯一）→ 拼随机后缀或自增序号
2. **忘了 PEXPIRE**：key 永不过期，内存只增不减
3. **窗口用固定值但业务按自然日**：跨天时要按日期重置，不能用滑动窗口逻辑

## FAQ

**Q：滑动日志能做到"绝对不超发"吗？**
在单 key 上可以（Lua 原子执行）。但分布式多 key（如按用户 + 按接口双维度）时，跨 key 的原子性无法保证，只能各自独立限流。

**Q：能不能用 List 代替 ZSET？**
可以，但 List 不支持按分数范围删除，清理过期记录要遍历，性能差。ZSET 的 `ZREMRANGEBYSCORE` 是 O(log N + M)。

**Q：滑动日志和令牌桶能组合吗？**
能。常见做法是"令牌桶控总量 + 滑动日志控单用户"，两层风控叠加。
