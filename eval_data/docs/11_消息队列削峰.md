# 消息队列削峰

削峰填谷是消息队列最核心的价值之一：把"瞬时高峰"变成"平稳消费"，保护下游系统不被流量洪峰打挂。

## 削峰的原理

```
秒杀瞬间：10 万请求/秒
    ↓ 写入 MQ（MQ 本身写入能力很强，10 万 QPS 轻松）
[========== 消息堆积 ==========]
    ↓ 消费者按自己的能力拉取（如 2000/秒）
订单服务：稳定 2000 QPS
```

**关键认知**：MQ 削的是"下游处理能力"的峰，不是"用户请求"的峰——用户还是要等，只是从"服务崩溃"变成"排队等待"。

## 适用与不适用

| 适合削峰 | 不适合削峰 |
|---|---|
| 下单（异步创建订单） | 查询（用户要立即看到结果） |
| 发短信/推送 | 支付回调（要同步确认） |
| 日志/埋点上报 | 库存扣减（要强一致） |
| 图片处理/转码 | 登录鉴权 |
| 积分/优惠券发放 | 任何"用户等结果"的同步链路 |

**判断标准**：这个操作**用户需要立即拿到结果吗**？需要 → 不能削峰；不需要 → 可以异步。

## 堆积了怎么办

MQ 堆积是削峰的正常状态，但堆积过多会引发问题：

| 堆积量 | 风险 | 处理 |
|---|---|---|
| < 10 万 | 正常 | 观察 |
| 10-100 万 | 消费延迟分钟级 | 扩容消费者 |
| > 100 万 | 磁盘告警、消息过期 | 紧急扩容 + 降级非核心消息 |

**扩容消费者的三个前提**：

1. **分区数足够**：Kafka 的消费者数不能超过分区数，扩消费者前先扩分区
2. **消费逻辑无状态**：有状态消费（如按用户顺序）无法简单扩容
3. **下游扛得住**：消费者扩容 10 倍，DB 可能先挂

## 消息可靠性

削峰场景下，"消息不能丢"比"消息不能重"更重要（重复可以幂等，丢失无法挽回）。

### 生产端

```java
// Kafka：acks=all + 重试
props.put("acks", "all");
props.put("retries", 3);
props.put("enable.idempotence", true);   // 幂等生产者，防重试重复
```

### 消费端

```java
// 手动提交 offset（处理成功后才提交）
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(100);
    for (ConsumerRecord<String, String> record : records) {
        try {
            handle(record);              // 业务处理
        } catch (Exception e) {
            // 处理失败：不提交 offset，或投递到死信队列
            deadLetter.send(record);
        }
    }
    consumer.commitSync();               // 成功才提交
}
```

## 一个真实的秒杀架构

```
用户 → 网关限流 → 秒杀服务
                      ↓ ① Redis 预扣库存（原子 Lua）
                      ↓ ② 发 MQ 消息（异步创建订单）
                   [MQ]
                      ↓ ③ 订单服务消费（限速 2000/s）
                      ↓ ④ 扣 DB 库存 + 创建订单
                      ↓ ⑤ 通知用户（WebSocket / 轮询）
```

**关键设计**：

- **Redis 预扣**：把"10 万人抢 1000 件"的竞争收敛到 Redis，只有 1000 个请求能发消息
- **MQ 限速消费**：订单服务按 DB 承受能力消费
- **用户轮询**：前端每 2 秒查一次"是否抢到"，而不是同步等待

## 常见坑

1. **MQ 当成数据库用**：消息保留 7 天，堆积 1 亿条，磁盘打满 → 设 retention + 监控堆积
2. **消费失败无限重试**：一条坏消息卡住整个分区 → 重试 3 次后进死信队列
3. **顺序消费误用**：为了"保证顺序"只用一个分区，削峰能力归零 → 只在必要时按 key 分区
4. **削峰后忘了限流**：消费者不限速，扩容 10 倍直接打挂 DB

## FAQ

**Q：削峰和缓冲有什么区别？**
本质一样，侧重不同：**缓冲**强调"吸收波动"（如日志批量写），**削峰**强调"把高峰削到下游能承受"（如秒杀）。

**Q：Kafka 和 RabbitMQ 削峰怎么选？**
Kafka 吞吐高（百万级）、适合日志/大数据；RabbitMQ 延迟低（微秒级）、支持复杂路由，适合业务消息。削峰场景两者都能用，Kafka 更抗堆积。

**Q：消息堆积会不会导致用户超时？**
会。堆积 100 万条、消费 2000/s，最后一条要等 500 秒。要么扩容，要么给用户"排队中"的明确反馈（而不是一直转圈）。
