# 线程池参数与拒绝策略

线程池是"用有限线程处理无限任务"的核心组件，但参数配错会引发 OOM、任务堆积、响应雪崩。

## 七个核心参数（Java ThreadPoolExecutor）

| 参数 | 含义 | 常见坑 |
|---|---|---|
| corePoolSize | 常驻线程数 | 设太小 → 频繁创建销毁 |
| maximumPoolSize | 最大线程数 | 设太大 → 上下文切换开销 |
| keepAliveTime | 空闲线程存活时间 | 配合 allowCoreThreadTimeOut 才有意义 |
| workQueue | 任务队列 | **无界队列 = 永不扩容线程 = 堆积 OOM** |
| threadFactory | 线程工厂 | 不命名 → 排查问题找不到线程 |
| handler | 拒绝策略 | 默认 AbortPolicy 直接抛异常 |
| allowCoreThreadTimeOut | 核心线程是否可回收 | 低频场景开启节省资源 |

## 执行顺序（很多人记错）

```
提交任务
  → 核心线程未满？创建核心线程执行
  → 核心线程已满 → 入队列
  → 队列已满 → 创建非核心线程（直到 maximumPoolSize）
  → 线程也满了 → 触发拒绝策略
```

**关键**：**队列满了才会扩容线程**，所以"无界队列 + maximumPoolSize"里的 max 永远不会生效。

## 参数怎么算

### CPU 密集型

```
线程数 ≈ CPU 核数 + 1
```

### IO 密集型

```
线程数 ≈ CPU 核数 × (1 + 平均等待时间 / 平均计算时间)
```

例：8 核，DB 查询平均 100ms，计算 10ms → `8 × (1 + 10) = 88` 个线程。

### 队列容量

**不要用无界队列**。推荐有界 + 合理的拒绝策略：

```
队列容量 ≈ 线程数 × 平均处理时间 × 可接受排队秒数
```

例：50 线程、每任务 200ms、能忍 2 秒排队 → `50 × 0.2 × ...` 实际取 **200-500** 比较稳妥。

## 四种拒绝策略

| 策略 | 行为 | 适用 |
|---|---|---|
| AbortPolicy | 抛 RejectedExecutionException | 需要调用方感知失败 |
| CallerRunsPolicy | 由提交线程自己执行 | **削峰**（提交线程变慢，自然限流） |
| DiscardPolicy | 静默丢弃 | 日志、埋点（丢了不心疼） |
| DiscardOldestPolicy | 丢队列最老的，再提交 | 只关心最新数据的场景 |

**生产环境推荐**：核心业务用 `CallerRunsPolicy`（背压），非核心用自定义策略（记录丢失数 + 告警）。

## 一个真实的配置示例

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    16,                                  // core：8核 × 2
    64,                                  // max：突发时扩容
    60L, TimeUnit.SECONDS,               // 空闲回收
    new ArrayBlockingQueue<>(500),       // 有界队列
    new ThreadFactoryBuilder()
        .setNameFormat("order-query-%d") // 必须命名
        .build(),
    new CallerRunsPolicy()               // 背压
);
```

## 常见坑

1. **`Executors.newFixedThreadPool` 的隐形无界队列**：`LinkedBlockingQueue` 默认容量 `Integer.MAX_VALUE`，任务堆积到 OOM 才报错
2. **`newCachedThreadPool` 的 maximumPoolSize = Integer.MAX_VALUE**：高并发下创建海量线程，直接 OOM
3. **拒绝策略静默丢弃**：`DiscardPolicy` 不抛异常不记日志，任务凭空消失，排查时毫无线索
4. **线程池不隔离**：一个业务把所有任务塞进同一个池，慢任务拖垮快任务 → 按业务分池

## 监控指标

- `activeCount`：活跃线程数（持续接近 max 说明容量不足）
- `queue.size()`：队列积压（持续增长说明处理不过来）
- `completedTaskCount`：完成数（算吞吐）
- `largestPoolSize`：历史最大线程数（判断 max 是否合理）

## FAQ

**Q：corePoolSize 和 maximumPoolSize 设成一样行吗？**
可以，等于固定大小线程池，配合有界队列 + CallerRunsPolicy 是**最稳**的生产配置。

**Q：线程池要不要用虚拟线程（JDK 21）？**
IO 密集型场景收益明显（不用为每个请求分配平台线程），但要注意：虚拟线程下 `synchronized` 会 pin 住载体线程，需要换 `ReentrantLock`。
