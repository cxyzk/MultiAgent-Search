# 幂等设计

幂等（Idempotency）指"同一操作执行一次和执行多次，结果相同"。在分布式系统里，网络重试、消息重投、用户重复点击都会导致重复请求，幂等是必须的设计。

## 为什么必须幂等

| 场景 | 重复的后果 |
|---|---|
| 支付回调重试 | **重复扣款** |
| 下单接口超时重试 | 创建两个订单 |
| MQ 消息重投 | 积分加两次 |
| 用户连点提交按钮 | 重复发券 |

**核心认知**：分布式系统里"恰好一次"（exactly-once）几乎不可能，只能做到"至少一次 + 幂等"。

## 四种实现方案

### 1. 唯一索引（最简单）

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    order_no VARCHAR(64) NOT NULL UNIQUE,   -- 业务唯一键
    user_id BIGINT NOT NULL,
    amount DECIMAL(10,2) NOT NULL
);
```

重复插入 → 唯一键冲突 → 捕获异常返回已存在的订单。

- **优点**：数据库保证，最可靠
- **缺点**：只适合"插入"类操作；冲突时要能优雅处理

### 2. 幂等 token（防重复提交）

```
① 前端请求"获取 token"接口 → 服务端生成 token 存 Redis（TTL 5 分钟）
② 前端提交时带上 token
③ 服务端 Lua 原子校验并删除 token
   - 存在 → 首次请求，继续处理
   - 不存在 → 重复提交，直接返回
```

```lua
-- KEYS[1] = idem:token:{token}
if redis.call('DEL', KEYS[1]) == 1 then
    return 1    -- 首次
end
return 0        -- 重复
```

- **优点**：适合所有写操作，不依赖业务唯一键
- **缺点**：需要前端配合；token 丢失会导致正常请求被拒

### 3. 状态机（防状态回退）

订单状态：`待支付 → 已支付 → 已发货 → 已完成`

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_no = ? AND status = 'PENDING';   -- 只有待支付才能改成已支付
```

`affected_rows = 0` → 说明状态已变，重复请求直接返回成功。

- **优点**：天然幂等，还能防"状态回退"（已支付又被改回待支付）
- **缺点**：只适合有明确状态流转的业务

### 4. 全局去重表（通用方案）

```sql
CREATE TABLE idempotent_record (
    idempotent_key VARCHAR(128) PRIMARY KEY,   -- 业务唯一标识
    biz_type VARCHAR(32) NOT NULL,
    result TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

```python
def handle(key: str, biz_type: str, fn):
    try:
        db.execute(
            "INSERT INTO idempotent_record (idempotent_key, biz_type) VALUES (%s, %s)",
            (key, biz_type)
        )
    except DuplicateKeyError:
        # 已处理过，返回上次结果
        return db.query_one("SELECT result FROM idempotent_record WHERE idempotent_key=%s", key)

    result = fn()                     # 执行真正的业务
    db.execute("UPDATE idempotent_record SET result=%s WHERE idempotent_key=%s", (result, key))
    return result
```

- **优点**：通用，能返回"上次的结果"
- **缺点**：多一次 DB 写；要注意"插入成功但业务失败"的补偿

## 幂等 key 怎么设计

| 业务 | 幂等 key |
|---|---|
| 支付回调 | `支付平台流水号` |
| 下单 | `用户ID + 客户端生成的 requestId` |
| MQ 消费 | `消息ID` |
| 定时任务 | `任务ID + 执行日期` |

**关键**：key 必须由**发起方**生成（客户端/上游），服务端不能自己生成（那就不是同一个 key 了）。

## 常见坑

1. **用 UUID 做幂等 key**：每次请求 UUID 都不同，等于没做幂等
2. **幂等 key 没有过期**：去重表无限增长 → 按业务设 TTL（如 7 天）
3. **先写业务再写幂等记录**：两步之间崩溃，业务成功但没记录，重试会重复执行 → **先占位再执行业务**
4. **只做接口层幂等，没做 MQ 层幂等**：消息重投照样重复消费

## FAQ

**Q：幂等和事务有什么区别？**
事务保证"要么全成功要么全失败"，幂等保证"重复执行结果一致"。分布式场景下两者要结合：本地事务 + 幂等消费。

**Q：Redis 做幂等可靠吗？**
不太可靠（可能丢数据）。Redis 适合做"防重复提交"（短 TTL、丢了影响小），**核心业务幂等应该落库**。

**Q：幂等 key 冲突了怎么办？**
返回上次的结果（如果有存），或返回"请求已处理"的明确错误码，让调用方知道不是失败。
