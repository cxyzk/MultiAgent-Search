# 网关限流实践

API 网关（Spring Cloud Gateway / Kong / APISIX）是限流的天然位置：所有流量必经，能拿到完整上下文（用户、路径、Header）。

## 为什么限流放网关

| 位置 | 优点 | 缺点 |
|---|---|---|
| 客户端 | 提前拦截 | 不可信，容易被绕过 |
| **网关** | 统一入口、能拿身份、不侵入业务 | 单点性能瓶颈 |
| 业务层 | 最细粒度、能感知资源 | 每个服务都要实现 |

**推荐组合**：网关做粗粒度（IP/用户/全局），业务层做细粒度（资源/热点参数）。

## Spring Cloud Gateway 的限流

基于 Redis + Lua 的令牌桶：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/order/**
          filters:
            - name: RequestRateLimiter
              args:
                key-resolver: "#{@userKeyResolver}"
                redis-rate-limiter.replenishRate: 50    # 每秒补充 50 个令牌
                redis-rate-limiter.burstCapacity: 100   # 桶容量 100
                redis-rate-limiter.requestedTokens: 1   # 每个请求消耗 1 个
```

**KeyResolver 决定限流维度**：

```java
@Bean
public KeyResolver userKeyResolver() {
    return exchange -> Mono.justOrEmpty(
        exchange.getRequest().getHeaders().getFirst("X-User-Id")
    ).defaultIfEmpty("anonymous");
}
```

- 按用户：`X-User-Id`
- 按 IP：`exchange.getRequest().getRemoteAddress().getHostString()`
- 按接口：`exchange.getRequest().getPath().value()`

## APISIX 的限流

```yaml
routes:
  - uri: /api/*
    plugins:
      limit-req:
        rate: 100          # 每秒 100 个
        burst: 200         # 允许突发 200
        key_type: var
        key: remote_addr
        rejected_code: 429
      limit-count:
        count: 1000        # 时间窗口内总次数
        time_window: 60
        key_type: var
        key: http_x_user_id
```

APISIX 的 `limit-req` 是**漏桶**，`limit-count` 是**固定窗口**，可以叠加。

## 网关限流的三个难点

### 1. 性能瓶颈

每次限流一次 Redis 往返，网关 QPS 高时 Redis 成为瓶颈。

**优化**：

- 本地缓存 + 定期同步（如每 100ms 从 Redis 同步一次配额）
- 用 Redis Pipeline 批量扣减
- 分层：本地令牌桶粗限 + Redis 精限

### 2. 分布式一致性

多网关实例共享 Redis 计数，但**Lua 脚本跨 slot 会失败**（集群模式）：

```lua
-- 错误：两个 key 可能在不同 slot
redis.call('INCR', 'rate:user:1')
redis.call('INCR', 'rate:api:order')

-- 正确：用 hash tag 强制同 slot
redis.call('INCR', '{limit}:user:1')
redis.call('INCR', '{limit}:api:order')
```

### 3. 降级策略

Redis 挂了怎么办？

| 策略 | 行为 | 适用 |
|---|---|---|
| fail-open | 放行，靠后端熔断 | 限流是优化项 |
| fail-close | 全部 503 | 限流是安全项（如防刷） |
| local-fallback | 切本地令牌桶 | **推荐** |

## 限流规则怎么定

1. **先压测**：测出单实例能承受的 QPS（如 800）
2. **留余量**：限流阈值 = 压测值 × 0.7（560）
3. **分接口**：核心接口（下单）严格、查询接口宽松
4. **分用户等级**：VIP 用户配额是普通用户 10 倍
5. **灰度调整**：先设高阈值观察，逐步收紧

## 常见坑

1. **限流阈值按"单机"配，实际是"全局限流"**：4 实例配 100，实际总放行 400
2. **KeyResolver 返回空**：所有匿名用户共用一个 key，互相影响
3. **429 没有 Retry-After**：客户端不知道等多久，立即重试加剧拥塞
4. **限流规则热更新没生效**：配置中心推送后网关没刷新，规则仍是旧的

## FAQ

**Q：网关限流和 WAF 有什么区别？**
WAF 防攻击（SQL 注入、CC 攻击），限流防过载。WAF 的 CC 防护本质也是限流，但规则更复杂（人机识别、行为分析）。

**Q：网关限流能防 DDoS 吗？**
不能。DDoS 流量在四层就打满了带宽，网关（七层）根本收不到请求。DDoS 要靠云厂商的高防 IP / 流量清洗。
