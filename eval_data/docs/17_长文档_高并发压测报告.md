# 高并发压测报告（长文）

本文记录一次针对订单服务的压测过程：目标、环境、脚本、结果分析和优化过程，可作为压测实施的参考模板。

## 一、压测目标

| 目标 | 指标 |
|---|---|
| 摸清单机承载上限 | 找到 QPS 拐点（响应时间开始陡增的点） |
| 验证限流阈值 | 确认 800 QPS 限流下系统稳定 |
| 发现瓶颈 | 定位 CPU/IO/连接池/锁竞争 |
| 验证扩容线性度 | 从 2 实例扩到 8 实例，QPS 是否接近线性 |

## 二、环境

### 压测机

```
4 台 8C16G（与生产同规格）
locust 分布式模式：1 master + 3 worker
```

### 被测服务

```
订单服务：4 实例，每实例 2C4G
DB：MySQL 8.0，8C32G，主从
Redis：4C8G 单实例
```

### 数据量

```
订单表：2000 万行
用户表：500 万行
热点商品：1000 个 SKU
```

## 三、压测脚本

### 场景设计

| 场景 | 比例 | 说明 |
|---|---|---|
| 查询订单详情 | 60% | 读多写少，走缓存 |
| 创建订单 | 30% | 写 DB + 扣库存 |
| 取消订单 | 10% | 状态流转 + 回滚库存 |

### Locust 脚本核心

```python
from locust import HttpUser, task, between

class OrderUser(HttpUser):
    wait_time = between(0.1, 0.5)

    def on_start(self):
        # 登录拿 token
        resp = self.client.post("/api/login", json={"user": "test", "pwd": "123456"})
        self.token = resp.json()["token"]
        self.headers = {"Authorization": f"Bearer {self.token}"}

    @task(6)
    def get_order(self):
        order_id = random.randint(1, 2_000_000)
        self.client.get(f"/api/order/{order_id}", headers=self.headers)

    @task(3)
    def create_order(self):
        payload = {
            "sku_id": random.randint(1, 1000),
            "count": random.randint(1, 3),
            "request_id": str(uuid.uuid4()),   # 幂等 key
        }
        self.client.post("/api/order", json=payload, headers=self.headers)

    @task(1)
    def cancel_order(self):
        self.client.post(f"/api/order/{random.randint(1, 100000)}/cancel", headers=self.headers)
```

**关键点**：

- `request_id` 用 UUID：避免压测数据被幂等逻辑拦截
- `wait_time` 模拟真实用户思考时间
- 三个场景按 6:3:1 加权

## 四、压测过程

### 第一轮：逐步加压

从 100 并发开始，每 2 分钟加 100，直到错误率超过 1%。

| 并发 | QPS | P50 | P95 | P99 | 错误率 | CPU |
|---|---|---|---|---|---|---|
| 100 | 480 | 45ms | 120ms | 210ms | 0% | 25% |
| 200 | 950 | 52ms | 180ms | 380ms | 0% | 48% |
| 300 | 1380 | 68ms | 320ms | 780ms | 0.2% | 72% |
| 400 | 1520 | 95ms | 680ms | 1.8s | 2.1% | 88% |
| 500 | 1480 | 180ms | 1.2s | 3.5s | 8.7% | 95% |

**拐点出现在 300-400 并发之间**：QPS 从 1380 涨到 1520（+10%），但 P99 从 780ms 涨到 1.8s（+130%）。

**结论**：单机稳定承载约 **1400 QPS**（4 实例 ≈ 5600 QPS）。

### 第二轮：定位瓶颈

400 并发时 CPU 88%，但 QPS 上不去，怀疑是锁竞争或 IO 等待。

**排查手段**：

```bash
# 1. 看火焰图
perf record -F 99 -p <pid> -g -- sleep 30
perf script | flamegraph.pl > flame.svg

# 2. 看 GC
jstat -gcutil <pid> 1000

# 3. 看线程堆栈
jstack <pid> | grep -A 20 "BLOCKED"
```

**火焰图结论**：**35% 的时间在 `ReentrantLock.lock()` 上等待**——库存扣减用了全局锁。

```java
// 问题代码：所有 SKU 共用一把锁
synchronized (this) {
    stock = stockMapper.selectForUpdate(skuId);
    if (stock < count) throw new SoldOutException();
    stockMapper.decrease(skuId, count);
}
```

**修法**：按 SKU 分段锁 + 乐观锁。

```java
// 修复后：乐观锁 + 重试
int affected = stockMapper.decreaseWithVersion(skuId, count, version);
if (affected == 0) {
    // 版本冲突，重试（最多 3 次）
    retry();
}
```

### 第三轮：优化后重测

| 优化项 | 效果 |
|---|---|
| 库存扣减改乐观锁 | 锁等待从 35% 降到 2% |
| 订单查询加本地缓存（Caffeine，TTL 5s） | DB QPS 下降 60% |
| 连接池从 20 调到 50 | 等待连接超时归零 |
| 日志改异步（Logback AsyncAppender） | P99 下降 80ms |

### 优化后结果

| 并发 | QPS | P95 | P99 | 错误率 | CPU |
|---|---|---|---|---|---|
| 300 | 2350 | 180ms | 420ms | 0% | 55% |
| 400 | 2900 | 320ms | 750ms | 0% | 72% |
| 500 | 3100 | 580ms | 1.4s | 0.8% | 85% |

**单机 QPS 从 1400 提升到 2900（+107%）**。

## 五、扩容线性度验证

| 实例数 | 总 QPS | 单实例 QPS | 线性度 |
|---|---|---|---|
| 1 | 2900 | 2900 | 100% |
| 2 | 5700 | 2850 | 98% |
| 4 | 11200 | 2800 | 97% |
| 8 | 21000 | 2625 | 90% |

**8 实例时线性度降到 90%**——因为共享的 MySQL 和 Redis 成为瓶颈。这说明：

- 无状态服务扩容接近线性
- **有共享依赖时，扩容收益递减**

## 六、限流阈值验证

按"压测值 × 0.7"设置限流：

```
单实例稳定 2900 QPS → 限流 2000 QPS
4 实例总限流 8000 QPS
```

**验证**：加压到 10000 QPS，观察：

- 限流拒绝率：20%（符合预期，多出的 2000 被拒）
- 错误率：0%（拒绝是 429，不是 500）
- P99：稳定在 800ms（没有雪崩）

**结论**：限流阈值有效，系统在超载时保持稳定。

## 七、压测中发现的坑

### 坑 1：压测机成为瓶颈

第一轮 500 并发时，压测机 CPU 打满（locust 是 Python，性能有限），测出来的 QPS 是假的。

**修法**：用 3 台 worker 分布式压测，压测机 CPU 控制在 70% 以下。

### 坑 2：数据倾斜

`random.randint(1, 2_000_000)` 生成的订单 ID 分布均匀，但真实流量是**热点集中**的（80% 请求集中在 20% 的热门商品）。

**修法**：按 Zipf 分布生成 SKU（`numpy.random.zipf(1.5)`），模拟真实热点。

### 坑 3：缓存预热不足

压测一开始 P99 就很高，因为缓存全是冷的，前 5 分钟都在查 DB。

**修法**：压测前先跑 5 分钟"预热流量"，让缓存命中率稳定后再开始统计。

## 八、经验总结

1. **压测要"逐步加压"**，一下子上 1000 并发看不出拐点
2. **看 P99 不看平均值**——平均 50ms 但 P99 5s 的系统，用户体验是灾难
3. **优化要有数据支撑**——火焰图指出锁竞争，才去改锁；拍脑袋优化等于赌博
4. **压测数据要逼近真实**——均匀分布 vs Zipf 分布，测出来的瓶颈完全不同
5. **压测环境要和生产一致**——规格、数据量、网络延迟，差一点结论就不可信
6. **扩容前先确认没有共享瓶颈**——否则加机器只是把压力转移到 DB
